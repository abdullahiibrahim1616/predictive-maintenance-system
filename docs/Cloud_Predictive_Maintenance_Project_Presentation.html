01 · The problem
Why this project matters

Maintenance is a decision problem

When asset condition is hard to see, action comes too late—or too soon.

For critical pumps, compressors, and other rotating assets, a failure can disrupt production, create urgent repair work, and complicate planning.

Reactive

Respond after failure

Teams may have limited warning, less time to prepare, and an urgent repair to coordinate.

Calendar-based

Service on a schedule

Fixed intervals are useful, but they may not reflect the asset’s actual operating condition.

Condition-informed

Use evidence to prioritize

Sensor readings and asset context can help teams investigate warning signs and plan work.

Project question: How can a practical software prototype turn selected equipment measurements into clear, traceable maintenance decisions?
Problem framing · no site loss figure is claimed in this deck02
02 · The aim
Purpose and intended achievement

Overall aim

Build a cloud-ready decision-support system for earlier, more informed maintenance.

The project brings equipment records, telemetry review, work-order coordination, and operational visibility into one software workflow.

The system is meant to help
  • Spot readings that cross configured warning rules.
  • Give teams a shared view of asset condition and open work.
  • Turn a signal into an accountable inspection or maintenance task.
  • Make the assumptions behind estimated benefits visible.
Intended achievement
Signal → decision → action

Demonstrate an end-to-end prototype that supports a more planned response to equipment risk—not claim that failures can be eliminated or predicted with certainty.

Project orientation: an operational decision-support prototype; plant staff remain responsible for interpreting alerts and authorizing work.

Aim · the overall change the project seeks to support03
03 · Objectives & scope
What the project will do—and not claim

Specific objectives

Deliver a usable workflow, then test whether it is useful.

  • Represent facilities, equipment, users, telemetry, and work orders in a shared application.
  • Accept vibration, temperature, pressure, and flow measurements for an asset.
  • Apply transparent condition rules and show a health indicator with an indicative RUL estimate.
  • Support alerts, work-order follow-up, audit visibility, and role-aware screens.
  • Show an illustrative cost-avoidance calculation with its assumptions.
  • Define a path to validate thresholds, data quality, usability, and operational benefit.
In scope for the prototype

Web interface, API, database-backed records, telemetry scoring, work orders, cost estimates, audit events, and optional AWS service integrations.

Not established by the current prototype

Live industrial sensor connectivity, a validated machine-learning model, production-proven RUL, guaranteed savings, offline field synchronization, or regulatory certification.

04 · Operating concept
How value is intended to flow

The maintenance decision loop

A useful alert is the start of a workflow—not the end of one.

The system connects a measurement to a reviewable action so that technical signals can be considered in maintenance planning.

01 · OBSERVE

Capture readings

Receive equipment measurements through a simulator or API.

02 · ASSESS

Check condition

Apply configured rules; calculate a health score and indicative RUL.

03 · PRIORITIZE

Raise a flag

Show abnormal conditions and create or update a work item.

04 · RESPOND

Review and act

Maintenance staff assess the alert, assign work, and record progress.

05 · LEARN

Measure results

Compare alerts, maintenance outcomes, downtime, and assumptions over time.

Human oversight: the prototype provides indicators and workflow support; it does not autonomously control equipment or replace engineering judgment.

06 · Assessment method
Transparent rules, honest limits

How the current prototype scores telemetry

Interpretable thresholds make the first version easy to inspect—and necessary to validate.

Vibration · mm/s
4.5 / 8.0

Configured warning / critical thresholds.

Temperature · °C
75 / 95

Configured warning / critical thresholds.

Pressure + flow
>1500 / <10k

Combined rule: pressure above 1,500 psi and flow below 10,000 bpd.

What the score means

Rule penalties are subtracted from 100 to form a 0–100 health index. Status bands and a health-below-65 rule support warning and work-order workflows.

What the score does not mean

The estimate is not trained on site failure histories. RUL is a code-defined heuristic, not a statistically validated failure forecast. Default thresholds need asset and operating-context review.

Source: backend/src/services/predictiveEngine.js. Treat example thresholds as prototype defaults, not safe operating limits.

A shared operational picture

Different users need different views of the same maintenance story.

Intended handoff: a flagged asset becomes a reviewed work order, an assigned task, and a recorded outcome. Reliable operational use depends on accurate asset data, clear ownership, and a verified response procedure.

The React application includes role-oriented views; the exact scope of each permission must be checked against configured server-side roles before an operational pilot.

09 · Trust & readiness
Controls must be matched to the deployment

Security and operational boundaries

Security features exist in the prototype; production assurance still requires deployment work.

Present in the project
  • Token-based authentication and role-oriented access routes.
  • Audit events for selected user and work-order actions.
  • Docker secrets for application and database credentials in the documented Compose setup.
  • Optional S3 telemetry archival, SNS notification delivery, and KMS integrations.
Before real operational use
  • Choose and harden cloud hosting, networking, TLS, IAM, and secret delivery.
  • Prove backups, recovery, monitoring, access reviews, and incident response.
  • Validate alert performance and work practices with asset specialists.
  • Review privacy, regulatory, and site safety requirements with responsible authorities.

Important: optional infrastructure and source-code controls do not by themselves establish a production deployment, end-to-end encryption, immutable audit storage, or regulatory certification.

10 · Roadmap & evaluation
How to move from prototype to evidence

A staged path to credible impact

Earn operational confidence in phases.

Now · prototype

Demonstrate the workflow

Exercise APIs, dashboards, rules, work orders, and audit records with controlled test data.

Next · validate

Ground the model

Review sensor quality, asset-specific thresholds, failure histories, and the RUL approach with engineers.

Pilot · integrate

Test in a bounded setting

Connect an approved data source, confirm response ownership, measure false alerts and useful lead time.

Scale · govern

Prove safe operation

Establish hosting, support, recovery, security assurance, and evidence-based value reporting.

Technical: ingestion reliability, data quality, alert precision / recall.
Operational: useful warning lead time, response time, work-order closure.
Business: verified downtime and repair outcomes, with transparent assumptions.

Set baselines and targets with the pilot stakeholders; this presentation does not invent a performance target.

Presenter guide · pages 1–6
Suggested talk track · approximately 5 minutes

Tell the story: problem, purpose, and design.

01 · Opening

Introduce the project as a cloud-ready maintenance decision-support prototype for rotating assets in Nigerian oil and gas operations. State that you will cover the problem, goals, current design, and the work still needed before an operational pilot.

02 · Problem

Explain the practical difficulty: teams need timely, trustworthy information to prioritize equipment work. Avoid quoting a broad downtime-cost figure unless you have an independently sourced, relevant site or industry reference.

03 · Aim

Describe the project aim in your own words: connect equipment signals to an understandable health view and a maintenance workflow. Emphasize that the software supports human decisions; it does not guarantee a prediction or prevent every failure.

04 · Objectives

Walk through the concrete objectives: organize asset data, accept selected measurements, apply visible scoring rules, support alerts and work orders, show an assumption-based financial estimate, and define how to evaluate usefulness. Be clear about items not yet proven.

05 · Workflow

Describe the five-step loop. The technical signal matters only if a responsible person reviews it, coordinates a task, records the outcome, and uses the evidence to improve the process.

06 · Architecture

Explain the React front end and Node/Express API, with database-backed asset, telemetry, and work-order records. Inputs currently come through the API or simulator; real plant sensors are not connected. AWS archival, notifications, and key functions are optional integrations.

Presenter guide · pages 7–12
Evidence, limitations, and defense questions

Tell the story: evidence, limits, and next steps.

07 · Assessment

Describe the current rule-based thresholds as transparent starting points. State plainly that the health index and RUL are heuristics, not an ML model validated on historical failures. Ask engineers to approve asset-specific limits before any pilot.

08 · Users

Explain how admin, maintenance, operations, and technician views support governance, planning, monitoring, and execution. The intended handoff is an alert, a reviewed work order, and a recorded maintenance result.

09 · Financial example

Show the arithmetic: 48 hours × $18,500 per hour = $888,000 gross avoided loss; less $42,000 repair cost gives an $846,000 illustrative net estimate. These are example assumptions, not measured savings. A real case needs approved site data and a defensible comparison.

10 · Readiness

Point out existing application controls and optional AWS integrations, then distinguish them from production assurance. Hosting, network/TLS, IAM, recovery, monitoring, testing, and compliance reviews must be addressed in the chosen environment.

11 · Roadmap

Propose a sequence: demonstrate with test data, validate with engineers and historical data, run a bounded pilot, then scale only after measured evidence and operational controls are acceptable.

12 · Close

Restate the project’s value as a bridge from equipment signal to accountable action. Invite questions about data validation, safe deployment, alert quality, or how financial outcomes will be measured.

“Is this machine learning?”

Suggested answer: Not in the current prototype. It uses configured threshold rules and a heuristic RUL mapping. A data-backed predictive model is a future step, subject to reliable historical failure data and validation.

“Has the system prevented downtime or saved money?”

Suggested answer: The code can calculate an illustrative estimate from assumed inputs. It has not established realized operational savings. A pilot would need verified downtime, costs, and an agreed comparison method.

“Is it live in the cloud with connected sensors?”

Suggested answer: The repository provides a local Compose deployment and optional AWS integrations. The deployment guide explicitly identifies application hosting and other production setup as remaining work; live field sensors are not connected.

“What is the next credible milestone?”

Suggested answer: Agree a bounded pilot, validate the measurements and thresholds with asset specialists, set baseline KPIs, and verify response procedures and production controls before connecting operational data.
